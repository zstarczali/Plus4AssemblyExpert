# DS Bug

- Source: https://plus4world.powweb.com/plus4encyclopedia/500292
- Category: Programming/General

Basics

The bug stems from **incorrect code handling** of the system's read-only variable pair, `DS` and `DS$`. Whenever DS is used, the appropriate value is automatically assigned to DS$, and vice versa. Memory for DS$ is allocated **differently** than other string variables, though its value is still placed in the standard string heap.

The bug

When assigning a new value to a string variable, the system's normal routine invalidates the old value in the heap, allocates new memory there, and completes the assignment. However, this routine contains a critical flaw at $8FC4: it explicitly checks whether the variable is DS$. This is an excess because the variable is read only and therefore it can't be invalidated in any case. The routine blocks invalidation if a variable's heap address matches the heap address of DS$. It fails to check if DS$ itself has already been invalidated. The system refuses to invalidate a string variable if it shares a heap address with an already invalidated DS$.

Impact

The bug causes two or even more distinct values to exist for a single variable on the heap. This confuses the garbage collector, which corrupts the RAM content, leading to various effects, some of them may be **subtle or strange**.

The bug condition

It is the sequence of four events:
1. the DS or DS$ value is used;
2. the disk operation is used, this invalidates DS/DS$;
3. the string assignment is used;
4. the garbage collector is invoked and this may corrupt memory.

These conditions do not always cause an issue when they occur. We also need that the address of the string variable in the heap that must be invalidated to be the same as the invalidated value of DS$. Furthermore, the effects of the bug depend on the contents of the heap and may sometimes be harmless.

So this bug can only corrupt your program/data in two cases::
1. your program uses strings intensively or for a long time;
2. the program is big and uses strings rarely and the heap is small due to the program size, which causes the GC to be invoked after a few string operations.

Two ways to bypass the bug

1. Do not use DS/DS$ at all. Use the disk drive command channel in the way intended for the C64. This is the best way and also prevents the [$FF28 bug](500015_ff28_bug.md) from occurring;
2. Put zero to $7B after any disk operation if DS/DS$ was used before it. Simply use POKE 123, 0.

Other info

The bug went undiscovered for 42 years. The exact reasons why DS$ is treated uniquely within the string heap remain completely unknown: The unique allocation behavior for DS$ may have been designed to make the code execute faster; perhaps the programmer responsible for the mistake may have been rushing under unrealistic deadline pressures. This bug was inherited by the C128.

Example code

`10 a$="aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
20 b$=a$
30 print ds$:directory
40 c$=a$
50 gosub1000
60 c$=a$+a$
70 b$=a$
80 gosub1000
90 print b$
100 end
1000 for i=1 to 1600
1010 d$="dddddddddddddddddddddddddddddddddddddddd"
1020 next
1030 return`

The printed value of B$ is the sequence of D instead of the sequence of A. The value of C$ is corrupted too. This code reveals the bug on the C128 too.
